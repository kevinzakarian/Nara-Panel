# NARA security and resource review — 0.8.1

Review date: **2026-10-18**. Scope: the panel-owned Python service, browser code, installation/upgrade scripts, systemd boundaries and dependency manifests. This is an engineering review with regression tests and dependency/static scans, not an independent penetration test or an audit of the upstream Sing-box/Cronet implementations.

## Findings and changes

| Area | Finding | Resolution |
| --- | --- | --- |
| Telegram workflow | Chat discovery silently read an empty password field far below the button, producing an incorrect-password error. | Discovery, connection testing and saving now each open an explicit, required administrator-password/2FA dialog. Missing bot tokens are caught before reauthentication. Unsaved token input is supported without saving or enabling delivery. |
| Bot testing | The existing delivery test required saved/enabled notifications and did not help validate a token during setup. | **Test bot** performs fixed-host HTTPS [`getMe`](https://core.telegram.org/bots/api#getme), shows only the bot's public name/username and sends no message. **Send test message** continues using the saved destination and private outbox. |
| Concurrent settings edits | Silent refresh could update the model revision while a settings form still contained old values. | Settings forms retain their rendered revision. Conflicting writes are rejected through the existing atomic validation/apply transaction. |
| REST maintenance status | The endpoint matched hexadecimal IDs; the broker generates URL-safe IDs containing capitals, `_` and `-`. | The route accepts the actual 32-character URL-safe format. |
| HTTP resources/framing | Thread-per-connection listeners had no application cap or idle timeout. Duplicate length/transfer-encoding and non-finite JSON were not explicitly rejected. | Each listener has at most 32 active handlers, a 15-second idle socket timeout and a bounded accept queue. JSON bodies require one Content-Length, no Transfer-Encoding, and the existing 1 MiB size limit; NaN/Infinity constants are rejected. |
| Origin/security tokens | Origin checks compared authority alone, and non-ASCII CSRF values could raise a comparison error. | Origins must be valid HTTP(S), match the authority and use HTTPS when secure cookies are required. Security-token comparison uses bytes and returns a normal rejection. |
| File publication | Atomic writes used a predictable temporary filename that could collide or follow a planted symlink. | Private, randomly named, exclusively created sibling files are flushed and atomically replaced, with cleanup on failure. |
| Release transport | Final release URLs were checked for HTTPS, but redirects could downgrade an intermediate request. | Both release check/download paths enforce HTTPS on the initial request and every redirect. Archive checksums and safe extraction remain required. |
| API read confidentiality | Some native service credentials (including Tailscale auth keys and certificate-provider/static keys) were missing from the read-only redaction list. | The list now covers the credential vocabulary from the pinned schema, with an actual API read/secrets-scope regression. Public keys remain readable. Rotate affected native service credentials if they were exposed to an untrusted Read-only integration on an earlier release. |
| API write pressure | Every authenticated request updated last-used metadata. | Last-used timestamps are written at most once per key per minute. Expiry/revocation checks still run on every request. |
| Notification idle work | The disabled/empty worker opened database connections every second. | A wake event handles new queue items/preferences; idle work sleeps up to 30 seconds, with scheduled retries and shutdown wakeup. |
| Core idle work | Every accounting tick rebuilt/validated the full configuration and reread its JSON even when account eligibility was unchanged. | Accounting remains every five seconds; a compact eligibility set triggers rebuilding only when quota/expiry eligibility changes. The baseline comes from the actual generated configuration, preserving expiry boundaries during startup. Zero traffic deltas do not create database writes. |
| Browser refresh | Every five-second tick downloaded state, metrics and entry settings. | Routine refresh fetches metrics/status; the full model is fetched when the active revision changes. Manual refresh/save still reloads all required state. Polling remains suspended for hidden tabs, open dialogs and maintenance. Repeated failure toasts are throttled. |
| UI state/secrets | Closed dialog content and late integration responses could outlive their visible operation/session. | Dialog close clears content/callback/config previews. Late integration cache responses are ignored after a session change. In-flight failures handle detached forms safely. |
| Inbound display | Native TLS could be labeled No TLS; an enabled inbound without eligible accounts could be labeled Active. | Native TLS is recognized. States distinguish Running, Waiting for clients, Core stopped and Disabled; transport labels use WebSocket/gRPC/HTTPUpgrade spelling. |

## Retained security boundaries

Administrator passwords use salted PBKDF2-SHA256 (600,000 rounds); browser sessions and API keys are stored as hashes. CSRF, same-origin checks, throttling and reauthentication remain enforced. TOTP setup verification, replay prevention and hashed single-use recovery codes remain covered by tests. Uploaded avatars stay bounded normalized PNGs with no external image URL or SVG execution. Client credentials remain independently generated; private profiles are bearer secrets. Subscription listeners expose no administration UI/API and retain the full supported 32–128-character legacy token range.

The native-service Read-scope disclosure affected the automation API introduced in 0.8.0 and is fixed in 0.8.1. Machine keys retain independent scopes, expiry, revocation and default secret-redacted reads. Configuration writes, including bulk operations, continue using core validation and rollback. Configuration-writing keys are powerful credentials: native Sing-box options can access files/network resources available to the unprivileged core. Root maintenance accepts fixed operations and verified fixed-repository releases; it does not execute arbitrary request commands. No new runtime package or frontend framework was added.

## Dependency/static checks

- `npm audit`: **zero reported advisories** in the current development dependency lockfile. Browser assets do not load packages from a CDN.
- `pip-audit`: current installed `grpcio 1.84.0`, `typing_extensions 4.16.0`, development `PyYAML 6.0.3` and `pip 26.2.1` reported **zero advisories** on the review date.
- The initial scan flagged the old development/bootstrap `pip 25.0.1`. It was upgraded locally. Fresh/full Linux installations and Docker builds now upgrade to `pip>=26.2,<27` before installing the unchanged runtime requirements. Panel-only upgrades preserve their existing Python environment; pip is installation tooling and is not invoked by normal web requests. See [official pip release notes](https://pip.pypa.io/en/stable/news/).
- Bandit findings were triaged against the code. Expected subprocess calls use fixed executables and argument arrays; test-only passwords and verification assertions are fixtures; all-interface binding is the intentional public listener/port-availability check. Traffic SQL now uses fixed whitelisted statements. Release HTTP openings go through the HTTPS-only helper. No finding is being represented as a successful exploit.

A final Ruff F-rule scan passed after six unused imports were removed from panel/maintenance/build helpers.

Actual test counts, native Linux results, browser checks and external-service limits are recorded in [VERIFICATION.md](VERIFICATION.md). Telegram responses are mocked in automated tests; no real bot message or production server change was performed during this review.

## 0.10 · Restore, export and SSH migration

Portable input is versioned JSON with a 12 MiB limit, explicit schema/counter validation and real-core validation before mutation; it is never extracted or executed. Public panel/subscription/server identities are taken from the destination, never the backup. Restore keeps destination administrator/2FA/API credentials and host accounting; proxy/client updates are backed up, and a failed start restores the previous model, quota counters and core. Private portable files are mode 0600 in a mode-0700 directory, retain 10 copies and require current-password/fresh-factor verification to download. CSV exports also require verification and neutralize spreadsheet formula prefixes.

Root SSH credentials require a secure panel origin (loopback preview exception), a separately verified SHA-256 host fingerprint, session/CSRF verification and fresh password/factor checks. The unprivileged source process runs fixed OpenSSH arguments and a constant destination command; user values are carried in the private stdin archive. Host checking is strict, local SSH config/agent discovery is disabled, and passwords never appear in process arguments, audit/job output or backups. Connection files are private and removed when the worker ends; the key editor disables autocomplete/spellchecking. A checksum-verified matching release is used on a fresh destination; existing installations are refused. The migration archive streams from a temporary file rather than retaining historical data in RAM. Source data and services are retained. Credentials/API key hashes and proxy keys are intentionally transferred to the explicitly approved destination; browser sessions are not copied.

Update confirmation requires a newly prepared, expiring backup proof tied to the same browser session. The browser requests its download before the separate final save-confirmation checkbox/installation step. The privileged updater still creates its complete private server snapshot before applying an update. Root backups exclude transient SSH connection directories.

This is a code/regression review, not an independent penetration test. Tests cover real key-authenticated SSH to a disposable Linux destination; password SSH and public-domain ACME issuance have not been exercised against a live external host.


## Client access and delivery review — 0.11.0

- Portal capabilities use domain-separated HMAC-SHA256 keyed by each random 256-bit subscription token. The endpoint performs constant-time comparisons, exposes only that account’s profile links/quota/expiry, and never serves administrator APIs/assets or private TLS keys. Subscription rotation invalidates the capability and bot binding. Exhausted/expired owners can read their own balance; the separate profile endpoint still enforces eligibility.
- Public page/assets use no-store, no-referrer, frame denial, no indexing, same-origin CSP and no external analytics/fonts/QR services. Portal JSON fetches omit cookies. Token-bearing paths are never logged. Public requests use bounded peer throttles in addition to bounded HTTP handler/socket limits. Plain HTTP is supported for existing installations; transport secrecy requires HTTPS. This is an engineering review, not a guarantee against every attack.
- Pairing tokens are random, SHA256-hashed at rest, expire after ten minutes, and are consumed transactionally once. Private-chat sender/chat IDs must agree. Message forwards and group/channel service commands are ignored. Username queries intersect already-paired accounts. Bindings include bot-token fingerprint and current portal capability; changing bot token disables client commands and cancels queued Telegram sends. No webhook is deleted automatically.
- Client sends require authenticated administrator session and CSRF protection; SMTP/template/bot preference changes and connection tests additionally require current password/2FA. Recipients are validated. Queued deliveries recheck current contact/binding, are bounded, expire after a day and retry at most three attempts. Deleted/changed recipients cancel jobs. Completed message history and pairing state are bounded/cleaned.
- SMTP always verifies certificates and requires implicit TLS or STARTTLS before authentication. Header controls are rejected; placeholders are allowlisted without attribute access/conversion/format specifiers, expansion is bounded, and HTML is escaped. QR PNGs are generated with vendored MIT code and standard-library raster encoding. No external image host is used. SMTP credentials are excluded from read responses/logs.
- External URL imports pin the connection to vetted public DNS results, revalidate every redirect, reject all non-global/mixed private addresses and HTTPS downgrades, verify TLS against the original hostname, ignore environment proxies and bound time/body/redirect/profile counts. Imported local files, commands, interfaces and references are rejected. Preview does not apply settings.
- A sleeping delivery worker wakes on preferences/jobs and uses no client scans while disabled. Account matching uses stable native user identities. Inbound match references remain valid while a quota temporarily removes a listener; live detour references remain strict.
- Portable backups include SMTP/template settings privately and restore with email/bot delivery disabled. They do not transfer host URLs. A fresh destination requires fresh private chat pairing.


## Connection and preference refinements — 0.12.0

Verified private-chat IDs are written to account metadata only after one-use pairing validation. Contact fields remain separate from authorization bindings; subscription rotation and bot changes still revoke access. Backfill intersects valid bot fingerprints and current per-account portal capabilities. Runtime configuration edits and contact changes share the runtime lock, with revision updates and no core restart. Portal output exposes only a connection boolean, not Telegram identity.

Traffic reads serialize core polling and reuse persisted cumulative counters; requests within one second reuse the latest sample. Alert-only and allowance-only writes preserve the other policy fields under the same lock. The unified Settings request validates the traffic policy before applying panel changes; managed access changes run last and report partial completion if that independent maintenance action fails.

Email previews escape subject/body and placeholders, use fictitious values, generate local cached QR images, and perform no message send or external image fetch. Update phase messages are fixed strings written atomically with the existing private maintenance-file ownership. No arbitrary commands, URLs or log content are added to progress responses.
